# 餐厅合规批处理 - 工程契约 v3

> spec v3.2, locked on 2026-05-09

---

## 整体架构
- Google Sheet：数据源 + 状态记录
- Apps Script Web App：Sheet 读写中转层
- Chrome 插件：所有自动化逻辑
- 不需要：Python 服务、Playwright、桌面图标

## host_permissions
- https://actionscenter.google.com/*
- https://admin.takeme.com/*

## Sheet 列结构
- A: google_id           输入
- B: restaurant_name     ①写入
- C: platform_id         ②写入
- D: result              最终结果
- E: error_reason        D=人工检查时填
- F: processed_at        ISO 时间戳

D 列枚举：合规无需操作 / 待关闭 / 已关闭 / 已关闭（原本就关闭） / 人工检查

- 合规无需操作：阶段 1 确认有在售 TakeMe Concierge 商品，无需操作
- 待关闭：阶段 1 确认不合规，等待阶段 2 重新校验后关闭
- 已关闭：阶段 2 执行关闭操作成功
- 已关闭（原本就关闭）：阶段 2 进入配置页发现已是 オプトアウト，幂等跳过
- 人工检查：任意步骤遇到异常，需人工介入

E 列枚举（仅 D=人工检查 时填）：
- 谷歌后台未找到
- 平台未找到
- 平台多个候选
- 店铺切换失败
- 当前状态为無効
- 配置页状态异常
- 保存操作失败
- 未知错误：{具体报错}

## 流程

### 步骤①：Action Center 抓餐厅名称
URL：https://actionscenter.google.com/inventory/merchants/{google_id}?a=2045466328
读取详情页 "merchant" 栏目下的店铺名称（trim 前后空格）。
读不到 → 谷歌后台未找到。

### 步骤②：TakeMe 搜索店铺
入口：https://admin.takeme.com/web/reservations/settings
把名称粘贴到"店舗設定"右侧搜索框（无需清空）。
等下拉候选：
- 0 → 平台未找到
- 1 → 解析出 platform_id（格式 "SR10193 - 餐厅名"，取 " - " 前的部分）
      按回车选中
- 多 → 平台多个候选

### 步骤③：商品管理 - 合规检查（只读）
URL：https://admin.takeme.com/web/reservations/settings#courses
安全检查：从"店舗設定"下拉框读出当前店铺名称，确认与目标一致；不一致 → 店铺切换失败。
操作：プラットフォーム 下拉选 "TakeMe Concierge" → 点「検索」→ 等列表。
判定：
- 列表至少 1 行 + 至少 1 行 ステータス = "表示" → 合规无需操作（跳过④）
- 列表为空 或 全部非"表示" → 不合规，进入 ④

### 步骤④：配置页 - 关闭操作（写）
URL：https://admin.takeme.com/web/reservations/settings#inbound-setting-tab
安全检查：同③。
读取「Googleマップに載せる」当前值：
- "オプトアウト" → 已关闭（原本就关闭）
- "有効" → 切换为 "オプトアウト" → 滚到页面底部 → 点保存
        → 1-2 秒内出现绿色提示「保存しました」 → 已关闭
        → 红色提示 → 人工检查 / 保存操作失败
- "無効" → 人工检查 / 当前状态为無効
- 其他/读不到 → 人工检查 / 配置页状态异常

## 触发方式
Chrome 插件 popup，分两阶段：
- 阶段 1（只读，①②③）：所有店跑一遍，结果落 Sheet
  - 不合规的行写 D="待关闭"，等待阶段 2 处理
- 阶段 2（写操作前重新校验，②③④）：仅处理 D="待关闭" 的行
  - 先重新走步骤 ② 搜索切换店铺
  - 再走步骤 ③ 重新判定合规性
    - 若变为合规 → 写 D="合规无需操作"，跳过 ④
    - 仍然不合规 → 继续走 ④
  - 再走步骤 ④ 关闭开关
  - 理由：阶段 1 和阶段 2 间隔未知，合规状态可能已变，写操作前必须重新验证

---

## 关键安全机制
- 幂等性：操作前先读当前状态
- 店铺一致性校验：进入③和④前从店舗設定下拉读当前店铺名核对
- 任何意外状态 → 人工检查，不冒险

## 变更纪律

本契约一旦锁定（见文件头版本号），后续任何修改必须遵守以下规则：

1. **Bump 版本号**：v3 → v4，并更新文件头的 locked on 日期
2. **记录改动原因**：在本文件末尾追加变更日志，注明改了什么、为什么改
3. **重新走 PM 确认**：修改不能由工程师单方面决定，须经 PM 审阅后方可生效
4. **代码与契约同步**：契约升版后，相关代码、DOM notes、Apps Script 需同步更新

> 目的：防止"口头修改"导致代码与文档失同步，保护后续接手人。
